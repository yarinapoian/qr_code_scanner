**Design doc: сканер QR-кодів**

**Мета і контекст**

Проєкт \- застосунок, який знаходить QR-коди на фото чи кадрі камери та показує закодований у них текст. Він складається з алгоритмічного ядра на Dart і Flutter-інтерфейсу до нього. 

Що реалізується з нуля:

* підготовка зображення: перетворення в чорно-біле з урахуванням нерівного освітлення;

* пошук QR на фото: три кутові квадрати, вирівнювальний квадрат, вирівнювання коду, знятого під кутом;

* декодування: службова інформація, зняття маски, виправлення помилок кодами Ріда-Соломона, розбір даних у текст.

Специфікація: ISO/IEC 18004:2015 (QR Code bar code symbology specification). Розділ стандарту з еталонним алгоритмом декодування береться за основу для пошуку і зчитування.

Еталонні реалізації (оракули для тестів): ZXing (zxing-cpp) і zbar для сканування, qrencode і Dart-пакет qr для генерації тестових кодів. Усі вони використовуються лише в тестах, не в коді ядра.

Мова і стек: Dart 3 і Flutter. Ядро \- окремий Dart-пакет без залежності від Flutter, тому тестується без емулятора. Для Dart є все потрібне для тестування: package:test, package:coverage, kiri\_check (property-based) і mutation\_test.

Чому тема практична: сканування QR з камери \- щоденна задача (оплата, квитки, меню), і саме вона містить найбільше складних випадків: освітлення, кут, розмиття, пошкодження.

**Обсяг проєкту**

MVP читає звичайні QR-коди всіх версій (1-40) і всіх рівнів корекції з фото, знятих у нормальних умовах. Рідкісні режими та інші типи кодів залишено поза межами.

| Область | У межах MVP | Поза MVP |
| :---- | :---- | :---- |
| Тип коду | QR Code Model 2, версії 1-40 | Model 1, Micro QR, rMQR, кольорові QR |
| Рівні корекції | L, M, Q, H | \- |
| Режими даних | numeric, alphanumeric, byte, ECI (тільки UTF-8 і ISO-8859-1) | Kanji, FNC1 (GS1), інші кодовані таблиці ECI |
| Кодування тексту в byte | ECI, а без нього перевірка: валідний UTF-8, інакше ISO-8859-1 | автовизначення інших кодувань (Shift\_JIS, CP1251) |
| Фото | будь-який поворот, нахил до \~30°, нерівне освітлення, помірний шум і розмиття | сильно вигнуті поверхні, рухоме розмиття, відеопотік з відстеженням |
| Варіанти вигляду | звичайний, інвертований (білий на чорному), дзеркальний | коди з логотипом понад запас корекції |
| Кілька кодів | до 4 кодів на одному фото, що не перекриваються | Structured Append (збирання одного повідомлення з кількох QR) |

**Архітектура**

Застосунок складається з Flutter-інтерфейсу і ядра. Ядро \- це три етапи конвеєра (image, detect, decode), якими керує QrScanner, і спільна основа common.

Правило залежностей: застосунок \-\> scanner \-\> (image, detect, decode) \-\> common. decode не знає про зображення, а detect \- про потік бітів. Ядро не використовує Flutter і dart:io, тому працює окремо і в тестах не потрібен емулятор.

Flutter-застосунок. Два екрани: сканування камерою і фото з галереї. Кадр камери приходить у форматі YUV420, і його Y-канал уже є масивом яскравості, тож передається в сканер без конвертації; фото з галереї декодує пакет image. Поверх зображення показуються знайдені кути коду і текст. У підрахунок алгоритмічного ядра інтерфейс не входить.

**Публічний API**

Бібліотека має два рівні API: QrScanner для звичайного користувача (фото \-\> текст) і QrMatrixDecoder для декодування вже зчитаної матриці модулів. Другий потрібен і для тестів: декодер можна перевіряти без зображень.

import 'package:qr\_scan\_core/qr\_scan\_core.dart';

final image \= LuminanceImage(width, height, bytes);

final scanner \= QrScanner(  
  options: const ScanOptions(  
    tryInverted: true,   
    tryMirrored: true,    
    maxCodes: 4,  
  ),  
);

final ScanReport report \= scanner.scan(image);

for (final code in report.codes) {       
  print(code.text);                      
  print(code.bytes);                       
  print(code.version);                     
  print(code.ecLevel);                     
  print(code.corners);                    
  print(code.correctedErrors);             
}  
for (final failure in report.failures) {   
  print(failure);                          
}

final DecodeResult r \= QrMatrixDecoder.decode(BitMatrix.fromRows(rows));  
switch (r) {  
  case DecodeSuccess(:final code): print(code.text);  
  case DecodeFailure(:final failure): print(failure);  
}

Сканер не кидає винятків на будь-яких вхідних даних: усі проблеми повертаються як значення класу ScanFailure. Виняток можливий лише при помилці програміста (наприклад, довжина bytes не дорівнює width × height).

| Помилка (ScanFailure) | Коли виникає |
| :---- | :---- |
| NotFound | на фото немає трьох кутових квадратів, що утворюють код |
| GeometryRejected | квадрати знайдено, але їхне розташування не дає валідного розміру коду |
| FormatInfoUnreadable | обидві копії службової інформації пошкоджені більше ніж на 3 біти |
| VersionMismatch | версія з version info не збігається з розміром, оціненим з фото |
| TooManyErrors | хоча б один блок має більше помилок, ніж можуть виправити коди Ріда-Соломона |
| MalformedData | потік бітів некоректний: невідомий режим, довжина виходить за межі, неправильне заповнення |
| UnsupportedMode | код використовує режим поза MVP (Kanji, FNC1, інший ECI) |

**Алгоритми**

Сканування \- це конвеєр: бінаризація \-\> пошук \-\> геометрія \-\> декодування.

1\. Бінаризація

Зображення ділиться на блоки 8×8, і поріг пікселя \- середня яскравість блоків навколо. Так тінь на половині коду не заливає її чорним, як це зробив би один поріг на все фото. Резервний метод \- глобальний поріг Оцу для маленьких зображень і дуже великих модулів.

2\. Пошук кутових квадратів

1. Скінченний автомат сканує рядки і шукає серії чорний-білий-чорний-білий-чорний у співвідношенні 1:1:3:1:1 (з допуском).

2. Кандидат перевіряється ще вертикально і по діагоналі, щоб відкинути хибні збіги на фоні. Близькі кандидати об'єднуються.

3. З кандидатів обираються трійки, що утворюють майже рівнобедрений прямокутний трикутник. Вершина прямого кута \- верхній лівий кут коду, а знак векторного добутку визначає два інші (і допомагає розпізнати дзеркальний код). Кожен квадрат належить лише одному коду, тому на фото може бути кілька кодів.

3\. Геометрія

1. Розмір коду оцінюється за відстанню між квадратами і розміром модуля та округлюється до 17 \+ 4v (v \- версія).

2. Для версій від 2 шукається вирівнювальний квадрат \- четверта точка, без якої не виправити перспективу.

3. Чотири пари точок задають перспективне перетворення (гомографію), яке знаходиться з системи 8 лінійних рівнянь. Для версій від 7 кожна ділянка між вирівнювальними квадратами має власне перетворення, щоб компенсувати викривлення об'єктива.

4. Колір кожного модуля береться з пікселя в його центрі.

4\. Декодування

1. Format info (рівень корекції і номер маски): 15 бітів у двох копіях; обирається найближче з 32 допустимих значень коду BCH(15,5), якщо відрізняється не більше ніж на 3 біти. Version info (від версії 7\) читається так само (код Голея (18,6)) і має збігатися з розміром коду.

2. Зняття маски (XOR з однією з 8 формул стандарту) і читання кодових слів зигзагом парами стовпців справа наліво, оминаючи службові зони.

3. Розчергування слів по блоках за таблицею стандарту (версія × рівень).

4. Виправлення помилок кодами Ріда-Соломона над GF(256): синдроми \-\> алгоритм Берлекемпа-Мессі (поліном локаторів) \-\> пошук Ченя (позиції помилок) \-\> алгоритм Форні (величини помилок) \-\> контрольна перевірка синдромів.

5. Розбір потоку бітів: індикатор режиму, лічильник символів (його довжина залежить від групи версій 1-9, 10-26, 27-40) і дані в режимах numeric, alphanumeric, byte, ECI.

5\. Порядок спроб

QrScanner пробує по черзі: локальну бінаризацію, глобальну, інверсію; якщо format info не читається \- дзеркальну орієнтацію. Порядок фіксований, тож одне й те саме фото завжди дає однаковий результат.

**Захист від неправильних даних**

Головна вимога до сканера: краще не прочитати код, ніж прочитати його неправильно. Неправильне посилання чи сума оплати небезпечніші за повідомлення «не вдалося».

Чого не можна гарантувати математично. Код Ріда-Соломона з n \- k корекційними словами точно виправляє до t \= ⌊(n \- k) / 2⌋ помилок. Якщо помилок більше, декодер іноді «виправляє» блок у інше валідне кодове слово (miscorrection), і це неможливо виявити на рівні одного блоку. Тому вимога «ніколи не повертати неправильні дані» формулюється так:

* в межах t помилок у кожному блоці результат завжди точний;

* понад t результат \- це TooManyErrors

**Стратегія тестування**

Для синтетичного фото ми точно знаємо текст, матрицю і кути коду, тому кожен етап сканера можна перевірити на тисячах випадкових входів. Реальні фото і порівняння з ZXing перевіряють, що синтетика не відірвана від реальності.

1\. Тестові дані

Власного генератора QR немає, тому в тестах коди створюють готові бібліотеки: Dart-пакет qr (швидко, прямо в тестах) і segno (коли потрібно задати версію, рівень, маску чи режим). qrencode незалежно перевіряє їхні матриці. Власний генератор синтетичних фото перетворює матрицю на зображення з поворотом, перспективою, шумом, розмиттям і нерівним освітленням та повертає справжні кути коду.

2\. Unit-тести

* арифметика GF(256) \- повним перебором усіх 256 × 256 пар;

* format info \- усі 32 значення з усіма варіантами пошкодження до 3 бітів;

* для кожної з 40 версій кількість модулів даних збігається з ємністю з таблиці стандарту;

* Ріда-Соломона: 0, 1, рівно t і t \+ 1 помилок;

* потік бітів: кожен режим, межі версій 9/10 і 26/27;

* бінаризація, пошук квадратів і гомографія на відомих зображеннях.

У назвах тестів на правила стандарту вказується пункт ISO/IEC 18004, щоб було видно, які частини стандарту покриті.

3\. Property-based тести (kiri\_check)

Більшість властивостей перевіряється на рівні функцій і декодера матриці \- це швидко, тисячі випадків за секунди. На рівні всього сканера випадків менше, бо кожен вимагає рендеру зображення.

* decode(encode(x)) \== x для випадкових рядків, усіх режимів і рівнів корекції;

* будь-яка з 8 масок читається, а не лише та, яку обрав генератор;

* пошкодження в межах запасу корекції виправляється точно; понад нього результат \- помилка або валідне кодове слово (див. розділ 6);

* текст \-\> QR \-\> синтетичне фото з випадковим викривленням у межах MVP \-\> сканер дає той самий текст;

* поворот, інверсія і дзеркальне відображення фото не змінюють 

* результат;

* K кодів на фото дають рівно K результатів.

4\. Диференційні та E2E-тести

* Корпус реальних фото: 100+ власних знімків (екран, папір, тінь, кут, кілька кодів) і публічні тестові зображення ZXing, до кожного \- очікуваний текст. Неправильних результатів має бути 0, а падіння частки прочитаних вважається регресією.

* Порівняння з ZXing і zbar на тих самих зображеннях: якщо обидва прочитали код, текст має збігатися. Це ловить випадки, коли сканер і тестовий генератор помиляються однаково.


5\. Граничні випадки

* дані рівно на межі ємності версії, порожні дані, версія 40;

* змішаний текст з цифр і літер, кирилиця і емоджі;

* код з навмисно найгіршою маскою (великі чорні плями заважають знайти кутові квадрати);

* інвертований, дзеркальний, обрізаний краєм кадру код (останній \- NotFound або правильний текст, ніколи неправильний);

* хибні квадрати на фоні, декілька кодів на одному фото;

* пошкоджена одна з двох копій format info.

6\. Fuzzing

Випадкові зображення будь-якого розміру (зокрема 0×0 і 1×1), випадкові матриці і байти не повинні викликати винятки чи зависання \- лише ScanFailure.
